    Section 1

    Claude Code 시작하기

    git·gh·파이썬을 설치하고, 작업 폴더를 Claude Code로 열어 지시 한 번으로 깃헙 저장소를 만든다. 자동 승인을 어디까지 허용할지도 정한다.

      Claude Code 시작하기

      설치: git · gh · 파이썬

      git변경 이력 기록

      파일이 언제 어떻게 바뀌었는지 기록하고 깃헙 저장소와 주고받는다. Claude Code가 코드를 저장·업로드할 때 내부에서 쓴다

      gh터미널에서 깃헙 조작

      GitHub 공식 명령줄 도구. “저장소를 만들어 줘”라는 지시를 Claude Code가 실행할 때 이 도구를 쓴다

      python검색 서버 실행

      파이썬 코드는 Claude Code가 쓴다. 다만 그 코드를 실행할 파이썬은 내 PC에 있어야 한다

      # Windows (PowerShell)
winget install --id Git.Git -e
winget install --id GitHub.cli -e
winget install --id Python.Python.3.13 -e
# macOS (터미널)
git --version ; python3 --version ; brew install gh
      # 설치 확인: 셋 다 버전 번호가 나오면 성공
git --version
gh --version
python --version
# 깃헙 로그인: 브라우저가 열리고 일회용 코드 입력
gh auth login --hostname github.com --git-protocol https --web
      앱 설치는 AI에게 물어 가며 진행한다. 오류 메시지나 설치 화면을 Claude에 그대로 붙여넣고 “다음에 뭘 해야 해?”라고 묻는다. 예: Windows에서 명령을 찾지 못하면 터미널 창을 새로 열기, brew가 없으면 Claude Code에 “gh를 설치해줘”라고 요청
      Claude Code 시작하기

      gh 로그인: 명령 한 줄이면 브라우저가 열린다

      질문에 Yes로 답하고, 화면에 뜬 일회용 코드를 복사한 뒤 Enter를 누르면 브라우저가 열린다. 브라우저에 코드를 붙여넣고 승인하면 끝난다.

      PS C:\claude\no-bullying> gh auth login --hostname github.com --git-protocol https --web
? Authenticate Git with your GitHub credentials? Yes
! First copy your one-time code: 1BC6-A269  ← 이 코드를 복사해 브라우저에 붙여넣는다
Press Enter to open https://github.com/login/device in your browser...
✓ Authentication complete.
- gh config set -h github.com git_protocol https
✓ Configured git protocol
✓ Logged in as kaist-itm-aibootcamp
      • 어느 폴더에서 실행해도 된다. 로그인은 폴더가 아니라 계정 단위다
      • 잘 되었는지는 gh auth status로 언제든 확인한다. “Logged in as” 뒤의 계정명이 내 계정인지 본다
      • 브라우저 기반 일회용 코드 방식(device flow)은 비밀번호를 터미널에 입력하지 않는 인증 방법이다
      Claude Code 시작하기

      작업 폴더를 열고, 지시 한 번으로 깃헙 저장소 만들기

      • 프로젝트 폴더를 만든다. 예: C:\claude\no-bullying (macOS ~/claude/no-bullying). 3강 산출물(판결문 rulings/, 임베딩 embeddings_json/, 요약 rulings_summary.csv)과 OpenRouter 키 파일을 이 안으로 옮긴다
      • 데스크톱 앱에서 Code를 고르고 이 폴더를 작업 폴더로 연다. Cowork와 달리 AI가 이 폴더 안에서 프로그램을 직접 실행한다
      현재 폴더 내용으로 깃헙 레포를 만들어서 작업하려고 해.
깃헙에 no-bullying이라는 레포를 만들어줘.
      • Claude Code가 git 초기화, 제외 파일 목록(.gitignore) 작성, gh로 저장소 생성과 업로드까지 진행한다. 공개 범위는 비공개(private)로 시작한다
      올리기 전에 직접 확인: github.com에서 저장소를 열어 키 파일이 없는지 본다. 이미 올라갔다면 파일을 지우는 것으로는 부족하다. 커밋 이력에 남기 때문이다. 해당 키를 폐기하고 새로 발급한다. 공개 저장소의 키를 자동으로 수집하는 프로그램이 상시 동작한다.

      권한: 자동 승인을 어디까지 허용할 것인가

      방식동작어울리는 경우
      매번 확인명령 실행·파일 변경마다 내용을 읽고 승인처음 쓰는 도구, 낯선 폴더, 민감한 자료
      선택적 허용같은 종류의 작업은 계속 허용반복 작업이 많은 실습 중반부터
      자동 승인대부분의 작업을 확인 없이 진행. 대량 삭제·외부 전송 같은 위험 작업은 따로 확인을 요청신뢰하는 폴더의 학습·개인 프로젝트
      • 오늘의 자료는 법원이 비실명화해 공개한 판결문이고, 잘못되어도 잃는 것은 폴더 하나다. 자동 승인을 켜도 된다
      • 회사 문서, 고객 정보가 든 폴더라면 다르다. 승인 수준은 §10에서 다룰 위험 분류와 함께 정한다

      검색엔진 구현: 단어가 아니라 의미로 찾기

      키워드 검색의 한계를 확인하고, 임베딩 유사도 검색엔진의 구조(색인과 검색)를 이해한 뒤, 계획서부터 대화로 Claude Code에게 구현을 맡긴다.

        검색엔진 구현

        두 가지 검색 방식: 키워드 매칭 vs 임베딩 유사도

        ①키워드 매칭
        • 질의어가 문서에 글자 그대로 있는지 확인한다
        • 구현이 쉽고 서버 없이 브라우저만으로 동작한다
        • 전통적 검색의 기본 방식
        ②임베딩 유사도
        • 질의와 문서를 같은 좌표계의 벡터로 바꾸어 거리를 잰다
        • 단어가 달라도 의미가 같으면 찾는다
        • 질의를 실시간으로 임베딩해야 하므로 API 호출이 필요하다

        판결문 요약 347건에 키워드 검색을 해 보면 세 가지 실패가 나타난다

        1동의어를 모른다

        “폭언” 90건, “욕설” 44건. 같은 현상인데 판결문이 어느 단어를 썼는지에 따라 결과가 갈린다

        2표현이 다르면 놓친다

        “예견가능성”은 5건. “회사가 알 수 있었다”라고 쓴 판결은 뜻이 같아도 찾지 못한다

        3의도를 모른다

        “괴롭힘을 인정하지 않은 사건”을 검색하면 “괴롭힘”, “인정”이 많이 나오는 인정 사건이 위로 올라온다

        검색엔진 구현

        임베딩 유사도: “비슷한 판결 찾기”를 “가까운 점 찾기”로

        • 판결문마다 4,096차원 벡터가 있다(3강에서 추출). 두 벡터의 코사인 유사도가 “의미가 얼마나 비슷한가”를 숫자로 나타낸다
        • 질의 문장도 같은 방식으로 벡터로 만들면 문장으로 검색할 수 있다. 실제 점검에서 “업무상 적정범위를 넘지 않았다고 보아 괴롭힘을 부정한 사례”라고 묻자 1·2위가 그 논리로 기각된 원고패 판결이었다. 단어가 아니라 판시 논리가 검색된 것이다

        데모 ② 유사 판례 찾기: 실제 코사인 유사도 (347건 전건 계산)

        🧭 기준 판결을 고르면 본문 임베딩이 가장 가까운 판결 5건을 보여준다

        이 데모는 왜 서버 없이 동작하는가: 347건끼리의 유사도는 미리 계산해 페이지에 넣어 둘 수 있기 때문이다. 문제는 사용자가 새 질의문을 입력하는 순간 시작된다. 그 문장의 벡터는 미리 계산해 둘 수 없다. 다음 장의 주제다.
        검색엔진 구현

        새 질의를 받으려면 백엔드가 필요하다

        • 347건끼리의 유사도는 미리 계산해 페이지에 넣어 둘 수 있다. 그러나 사용자가 새로 입력한 문장의 벡터는 미리 계산할 수 없다. 검색할 때마다 임베딩 API를 불러야 한다
        문제 1. 호출마다 비용
        질의 하나는 1원 미만이지만, 공개된 웹앱이라면 누가 몇 번 검색할지 통제할 수 없다. 비용은 내 크레딧에서 나간다.
        문제 2. 키를 숨길 곳이 없다
        브라우저 자바스크립트에 API 키를 넣으면 누구나 개발자도구(F12)로 키를 복사해 내 크레딧으로 호출할 수 있다. 정적 웹페이지에는 비밀을 둘 곳이 없다.

        사용자 입력을 실시간으로 처리하고 비밀(키)을 지키려면 키를 가진 중간 프로그램, 백엔드가 필요하다

        검색엔진이 문서 목록을 돌려준다면, RAG는 검색된 문서를 AI의 컨텍스트에 넣고 그 문서만 근거로 답변을 쓰게 한다. 근거 번호를 인용하고, 근거가 없으면 답하지 않는 판례 챗봇을 만든다.

          RAG 적용

          RAG(Retrieval-Augmented Generation)란 무엇인가

          • LLM에게 그냥 물으면 학습 데이터에 기초해 답한다. 이 방식에는 세 가지 한계가 있다: 학습 이후의 일을 모르고, 내 데이터(사내 문서, 수집한 판결문)를 모르고, 모르는 내용도 그럴듯하게 지어낸다(환각)
          • RAG: 질문이 들어오면 관련 문서를 검색(Retrieval)해 질문과 함께 컨텍스트에 추가(Augmented)하고, 그 문서를 근거로 답을 생성(Generation)하게 한다
          🆕최신·내부 데이터

          모델이 학습한 적 없는 문서(어제 수집한 판결문, 사내 규정)로 답할 수 있다

          왜 Chat·Cowork가 아니라 유료 API인가

          👤Chat · Cowork: 사람이 쓰는 도구
          • 사람이 로그인해 화면에서 직접 실행하는 개인용 서비스
          • 내 연구·업무를 내가 할 때는 이것으로 충분하다
          • 그러나 내 프로그램(서버)이 대신 호출할 수 없고, 계정 1인분이다. 이용자 100명을 받을 수 없다
          ⚙️외부 API: 프로그램이 부르는 인터페이스
          • 서버가 자동으로, 동시에, 사람 없이 호출한다
          • 쓴 만큼 과금. 이용자가 늘면 비용도 비례해 늘어나는 구조
          • 챗봇·웹앱 같은 서비스는 일반적으로 이 구조를 쓴다

          이 구분은 §8에서 업무 자동화의 형태(스킬 vs 웹앱)를 고르는 기준이 된다. 법적으로도 다르다: 개인 구독 서비스의 약관과 API 이용 약관은 데이터 학습·보존 조건이 다를 수 있다(§10).

            • 문서 하나를 벡터 하나로 나타내는 방식은, top-k로 돌려줄 수 있는 문서 조합의 수가 임베딩 차원에 의해 상한이 정해진다. k=2인 단순한 경우에도, 시험 데이터에 직접 맞춰 학습한 임베딩에서도 한계가 나타난다
            • LIMIT 데이터셋: “○○는 △△를 좋아한다” 같은 단순한 문장과 “△△를 좋아하는 사람은?” 질의. 문서 5만 건 버전에서 최상위 임베딩 모델들도 recall@100이 20% 미만. 같은 과제에서 키워드 기반 BM25는 훨씬 나았다
            더 좋은 임베딩 모델로 바꾸면 해결된다는 기대에는 한계가 있다. 질의가 여러 조건의 조합을 요구할수록(예: “2020년 이후, 근로자 패소, 연장근로수당 쟁점”) 벡터 하나로는 다 표현하지 못한다. 조건 검색은 메타데이터 필터나 데이터베이스 질의로 처리한다.
            RAG의 한계 · 검색 단계

            검색 단계 실패 (2): 부정어, 숫자·정확한 용어, 그리고 긴 문맥

            ¬부정어를 구별하지 못한다

            NevIR (Weller 외, EACL 2024): 부정 표현 유무만 다른 문서 쌍에서 두 질의 모두의 순위를 맞히게 했더니, 대부분의 최신 검색 모델이 무작위 순위와 비슷하거나 그보다 나빴다. “해고가 정당하다”와 “해고가 정당하지 않다”, 책임을 인정한 판결과 인정하지 않은 판결은 임베딩 공간에서 매우 가깝다

            #숫자·조문 번호·정확한 용어

            금액, 날짜, 사건번호, “제76조의2” 같은 정확한 일치가 필요한 검색에는 의미 검색보다 키워드 검색이 적합하다. 실무에서는 두 방식을 섞는다(하이브리드 검색). Anthropic이 BM25를 병행하는 이유로 든 것도 정확한 용어 일치다. 다만 이 약점을 수치로 측정한 대표 연구는 아직 확인하지 못했다

            ⋯많이 넣을수록 중간을 놓친다

            Lost in the Middle (Liu 외, TACL 2024): 정답이 입력의 처음이나 끝에 있을 때 가장 잘 찾고 중간에 있을 때 크게 떨어지는 U자형. GPT-3.5는 문서 없이 56.1%, 정답 문서 하나만 주면 88.3%였는데, 문서 20개 중 가운데에 정답을 두면 문서를 주지 않은 경우보다 낮아지기도 했다. 우리 챗봇과 같은 20건 설정이다

            Context Rot (Chroma 기술 보고서, 2025): 18개 모델 모두 입력이 길어질수록 성능이 떨어졌다. 단순한 과제에서도 그랬고, 정답과 비슷한 방해 문장이 있을 때 더 떨어졌다. top-20에는 정답과 비슷하지만 결론이 다른 판결이 섞이기 마련이다. 동료 심사를 거친 논문이 아니라 벡터 DB 회사의 보고서라는 점은 감안한다.
            데모 ①로 돌아가 보면: “괴롭힘을 인정하지 않은 사건”은 키워드 검색의 실패 사례였다. 임베딩 검색은 이 질의에서 성공했지만(§2), 부정어 처리가 항상 성공한다는 보장은 없다. 결론이 중요한 질의는 결과 목록의 소송결과 칸을 직접 확인한다.
            RAG의 한계 · 보안과 프라이버시

            보안과 프라이버시: 검색 자료가 공격 경로가 되고, 벡터도 원문을 드러낸다

            ☣지식 DB 오염 (PoisonedRAG)

            Zou 외, USENIX Security 2025. 수백만 건 규모의 지식 DB에 목표 질문당 악성 텍스트 5개를 넣어 공격자가 고른 답을 내게 하는 공격의 성공률이 90%. 저자들이 검토한 기존 방어 기법으로는 충분히 막지 못했다. 사용자 업로드 문서, 웹에서 수집한 자료를 DB에 섞기 시작하면 이 위험이 생긴다

            ↪간접 프롬프트 주입

            Greshake 외, AISec 2023. 공격자가 LLM이 나중에 읽을 웹페이지·문서·이메일에 지시문을 숨겨 두면, 사용자가 아닌 제3자가 모델의 행동을 바꿀 수 있다. Bing Chat 등 실제 시스템에서 시연했다. RAG에서 검색된 문서는 “데이터”이지만 모델에게는 “지시”로도 읽힌다. 데이터와 명령의 경계가 구조적으로 없다

            ⟲임베딩 역추적

            Morris 외, Text Embeddings Reveal (Almost) As Much As Text, EMNLP 2023. 임베딩만 보고 원문을 반복 수정하며 복원하는 방법으로 32토큰 입력의 92%를 정확히 그대로 복원했다. 임상 기록 임베딩에서 환자 성명 같은 개인정보도 복원할 수 있음을 보였다

            법적 질문 (6강과 연결): 개인정보가 담긴 문서를 임베딩한 벡터 DB는 개인정보인가? 원문만 지우고 벡터를 남기면 파기한 것인가? 위 연구에 비추면 임베딩도 원문을 상당 부분 복원할 수 있는 정보다. 벡터 DB에도 접근 통제, 안전조치, 파기 의무를 같이 적용하는 것이 안전한 해석이다(논문의 주장이 아니라 법적 해석이다). 개인정보를 외부 임베딩 API로 보내는 것 자체도 처리위탁·국외 이전 검토 대상이다.

            (2024 BCCRT 149, 2024. 2.)            		조모상을 당한 승객에게 웹사이트 챗봇이 “일반 운임으로 예약한 뒤 사별 할인을 소급 신청할 수 있다”고 안내. 실제 정책은 소급 신청 불가항공사는 “챗봇은 스스로 책임지는 별개 주체”라고 항변했으나 배척. 웹사이트 정보는 정적 페이지든 챗봇이든 회사가 책임진다(부주의한 허위 진술). 배상 CAD 650.88, 이자·수수료 포함 812.02
            뉴욕시 MyCity 챗봇
            (2024. 3. 보도)            		시 공식 자료를 바탕으로 사업자에게 규정을 안내하는 공공 챗봇이 “주거 바우처 세입자를 거절해도 된다”, “직원 팁 일부를 가져가도 된다”는 위법한 답을 함. 같은 질문에 답이 달라지기도 함당시 시장은 운영을 유지. 2026. 1. 새 시장이 “기능적으로 쓸 수 없다”며 폐지 계획 발표. 공식 자료를 근거로 해도 답의 적법성은 보장되지 않는다
            Cursor 고객지원 봇 “Sam”
            (2025. 4.)            		여러 기기에서 로그아웃되는 문제 문의에 “구독당 기기 1대만 허용하는 보안 정책”이라고 답함. 그런 정책은 없었고 Sam은 AI였다공동창업자가 공개 사과, 이후 AI 응답임을 표시하기로 함. 자료에 답이 없을 때(FP1) “모른다” 대신 정책을 지어낸 사례
            Deloitte 호주 보고서
            (2025)            		정부에 제출한 237쪽 보고서에 존재하지 않는 참고문헌과 지어낸 판결 인용. 수정본에서 GPT-4o 기반 도구 사용을 밝힘계약(약 AUD 44만)의 마지막 분할금 환불. RAG 사례는 아니지만 검증하지 않은 인용의 전문가 책임 사례

            1자료에 없는 질문

            347건에 없는 쟁점을 묻는다(예: “육아휴직 후 복귀 거부로 인한 손해배상”). 정해진 거절 문구가 나오는지, 일반론으로 그럴듯하게 답하는지 본다 (FP1)

            2부정·결론을 묻는 질문

            “회사 책임을 부정한 판결만”처럼 결론을 지정한다. 근거 카드의 소송결과가 실제로 그 결론인지 확인한다

            3숫자를 묻는 질문

            “위자료 3천만 원 이상 인정된 사건”. 금액 조건은 임베딩이 잘 다루지 못한다. 답변의 금액을 카드·전문과 대조한다

            4인용 대조

            답변의 문장 하나를 골라, 붙은 번호의 판결 전문을 열어 그 문장을 실제로 뒷받침하는지 읽는다. 번호가 있는 것과 뒷받침하는 것은 다르다(misgrounded)

            챗봇 디버깅용 기능을 추가해줘. 관리자 화면에서 각 질문에 대해
(1) 검색된 20건의 순위·사건번호·유사도·소송결과를 함께 보여주고
(2) 답변에 인용된 번호마다 해당 요약의 첫 문장을 나란히 표시해서
내가 인용이 문장을 뒷받침하는지 눈으로 대조할 수 있게 해줘.
틀린 답을 발견하면 "검색 실패"와 "생성 실패" 중 무엇인지 표시해 기록할 수 있게 해줘.

            이렇게 모은 실패 사례 20~50건이 §10에서 다룰 평가 세트가 된다. 과제 발표의 “신뢰성” 부분에 쓴다.

            검색키워드(BM25) + 임베딩 하이브리드, 조각에 사건명·법원·쟁점 붙이기, 재순위화, 소송결과·연도 같은 조건은 메타데이터 필터로최선의 조합에서도 검색 실패가 남는다(Anthropic 실측 1.9%). 임베딩의 이론적 한계

            보안검색 문서 안의 지시문을 따르지 않도록 하는 지시, 업로드 자료 검토, 벡터 DB 접근 통제간접 프롬프트 주입을 완전히 막는 방법은 아직 없다
            운영로그(§7)로 실패 사례를 모으고 평가 세트로 측정(§10), 화면에 한계 고지, 사람이 최종 확인운영자 책임은 남는다(Air Canada)

              URL이 생기는 순간 무엇이 달라지는지 정리한다. 가장 간단한 비밀번호 잠금(해시 + 환경변수)에서 출발해, 이메일 6자리 인증코드로 명단의 사람만 쓰게 하고, 그 밖의 인증 기법과 권한 설계를 개관한다.

                인증과 권한

                URL이 생기는 순간 달라지는 세 가지

                🤖모르는 방문자

                초대한 사람만 오지 않는다. 흔한 주소 패턴을 자동으로 두드리는 봇은 배포 직후부터 접속한다. vercel.app 주소는 생각보다 쉽게 퍼진다

                💸비용은 내 계정으로

                서비스가 부르는 API(임베딩·LLM) 요금은 전부 내 키로 청구된다. 누가 얼마나 쓰게 할지 내가 정해야 한다. 키에 사용 한도를 걸어 두는 것이 1차 안전장치다

                ⚖️데이터의 책임

                서비스에 담긴 데이터와 서비스가 수집하는 데이터(질문, 이메일)의 관리 책임이 나에게 생긴다. 개인정보 보호법상 개인정보처리자가 될 수 있다

                사례: 2021년 국내 챗봇 서비스 ‘이루다’는 연인 간 대화 데이터로 학습했는데, 실명·주소 등이 응답으로 노출된 사례가 드러나 서비스가 중단되었고 개인정보보호위원회의 과징금·과태료 처분을 받았다. 개인정보가 섞인 데이터를 서비스에 실어 공개하면 그 정보의 제공자가 된다.
                인증과 권한

                접근 통제는 공개·비공개의 둘이 아니라 4단계다

                수준누가 들어오나예맞는 데이터
                1. 완전 공개누구나, 검색엔진에도 노출3강의 GitHub Pages 소개 사이트공개해도 아무도 피해를 입지 않는 정보
                2. URL만 아는 사람주소를 받은(또는 추측한) 누구나§5에서 배포한 챗봇의 첫 상태민감하지 않은 것. 보안 수단이 아니라 노출을 줄이는 정도임을 알고 쓴다
                3. 인증된 사람명단에 있고 본인임을 증명한 사람오늘 만드는 이메일 인증코드내부 자료, 팀 데이터, 비용이 드는 기능
                4. 권한별 차등인증된 사람 중에서도 역할별로관리자 화면과 일반 화면 분리(§7)타인의 개인정보, 삭제·결제처럼 되돌릴 수 없는 조작

                수준을 고르는 질문: “이것이 유출되면 누가, 얼마나 피해를 입는가”

                • 접근 통제는 데이터 단위로 정한다. 같은 서비스 안에서도 챗봇 화면은 2~3, 문답 기록 열람은 4일 수 있다
                • 인증(authentication)은 “너는 누구인가”를 확인하는 절차, 인가(authorization)는 “확인된 너는 무엇을 할 수 있나”를 정하는 규칙이다. 인가는 인증을 전제로 한다. 오늘은 인증을 만들고, 인가는 “인증된 사람은 모두 같은 권한”으로 시작한다
                인증과 권한

                가장 간단한 잠금의 재료: 해시(hash)란 무엇인가

                • 해시 함수는 어떤 길이의 입력이든 받아서 정해진 길이의 문자열(해시값)을 내놓는 함수다. SHA-256은 입력이 한 글자든 책 한 권이든 항상 64자리 16진수(256비트)를 낸다
                # 실제 SHA-256 계산 결과
kaist2026  →  5391049cb77f42e054372ef575adc8c88a8000ef63fcd48203fa10fd4d4c3d4e
kaist2027  →  ff88f3baea2d5fb57236735d592127c1733d4915540310728193df425beb7193   ← 숫자 하나만 바꿈
Kaist2026  →  9dce81ff753e1363ad924a7a7ecceaf5508258cf322aa8702f71a00171676ca9   ← 대문자 하나만 바꿈
                1같은 입력, 같은 출력

                언제 어디서 계산해도 kaist2026의 해시는 같다. 그래서 “입력값을 해시해 저장된 해시와 비교”하는 방식으로 비밀번호를 확인할 수 있다

                2되돌릴 수 없다

                해시값에서 원래 입력을 계산해 내는 방법이 없다(일방향). 그래서 해시값이 노출되어도 원래 비밀번호가 바로 드러나지 않는다

                3조금만 달라도 전혀 다르다

                한 글자만 바뀌어도 해시값이 완전히 달라진다. 비슷한 비밀번호인지조차 해시값으로는 알 수 없다

                4같은 해시를 만드는 다른 입력을 찾기 어렵다

                현재 기술로 SHA-256의 해시값이 같은 서로 다른 두 입력을 찾아낸 사례가 없다(충돌 저항성)

                이미 보았던 해시: Vercel 배포 목록의 커밋 번호 2b81927은 git이 커밋 내용을 해시한 값의 앞부분이다(§5). 파일을 내려받을 때 함께 제공되는 “체크섬”도 해시다. 내용이 한 글자라도 바뀌면 값이 달라지므로 변조 여부를 확인하는 데 쓴다.
                인증과 권한

                해시만으로 충분한가: 약점과 보완, 그리고 법적 의무

                약점: 되돌릴 수는 없지만 “추측해서 맞춰 볼” 수는 있다

                • 무차별 대입: 후보 비밀번호를 하나씩 해시해서 같은 값이 나오는지 본다. SHA-256은 빠르게 계산되도록 설계되어 있어 일반 GPU로도 초당 수십억 번 시도할 수 있다
                • 미리 계산한 표: 123456의 해시는 누가 계산해도 8d969eef…6c92다. 흔한 비밀번호의 해시를 미리 계산해 둔 표가 공개되어 있어, 짧거나 흔한 비밀번호는 해시값만 보고 바로 찾아진다

                보완

                • 솔트(salt): 사용자마다 다른 임의 문자열을 붙여서 해시한다. 같은 123456이라도 k7Qz를 붙이면 756220f0…1598, Xp2m을 붙이면 596e4d6c…8400. 미리 계산한 표가 쓸모없어진다
                • 느린 해시: bcrypt, scrypt, Argon2처럼 일부러 계산을 느리게(수십~수백 밀리초) 만든 함수를 쓴다. 정상 로그인에는 문제가 없지만 수십억 번 시도는 사실상 불가능해진다
                • 긴 비밀번호: 문장형으로 길게 정하면 시도해야 할 경우의 수가 급격히 늘어난다
                상황적정 수준
                나 혼자 쓰는 웹앱의 사이트 비밀번호 (오늘의 지름길)SHA-256 해시 + 환경변수 + 긴 문장형 비밀번호
                여러 사람의 회원 비밀번호를 저장하는 서비스솔트 + 느린 해시(bcrypt, Argon2). 직접 구현하지 말고 검증된 라이브러리나 인증 서비스 사용
                법적 의무: 개인정보보호위원회 「개인정보의 안전성 확보조치 기준」(고시)은 개인정보처리자가 비밀번호를 저장할 때 복호화되지 않도록 일방향 암호화해 저장하도록 정한다. 다른 사람의 비밀번호를 받는 서비스를 만들면 이 의무가 적용된다. 개인정보 보호법 제29조(안전조치의무)의 구체화다.
                해시와 암호화의 차이: 암호화는 키가 있으면 원래대로 되돌릴 수 있다(양방향). 해시는 누구도 되돌릴 수 없다(일방향). 비밀번호는 원래 값을 다시 볼 필요가 없으므로 해시로 저장한다. 반대로 API 키처럼 서버가 원래 값을 써야 하는 비밀은 해시할 수 없어서 환경변수에 원문을 둔다.

                가장 간단한 잠금: 비밀번호 해시를 환경변수에 두기

                • 비밀번호를 코드에 그대로 적으면 GitHub에 올라가는 순간 공개된다. 그래서 앞 장의 해시를 쓴다: ① 내 비밀번호의 SHA-256 해시를 만들고 ② 그 값을 Vercel 환경변수 PASSWORD_HASH에 넣고 ③ 사이트에 비밀번호 입구를 단다
                • 서버에는 비밀번호의 해시값만 두고, 입력값을 해시해 같은지 비교한다. 환경변수가 노출되어도 원문은 복원되지 않는다
                비밀번호 문자열을 SHA-256으로 해시해 16진수 문자열로 출력하는
아주 짧은 파이썬 스크립트를 만들어 실행해줘.
비밀번호는 실행할 때 내가 직접 입력할게 (코드나 대화에 남기지 않게).
                배포한 사이트에 비밀번호 입구를 달아줘.
1. 첫 화면에서 비밀번호 하나만 입력받는다.
2. 서버(/api/login)는 입력값을 SHA-256으로 해시해 환경변수
   PASSWORD_HASH와 비교하고, 일치하면 세션을 발급한다.
3. 세션이 없으면 화면과 모든 API가 동작하지 않아야 한다.
4. 틀렸을 때는 "비밀번호가 올바르지 않습니다"만 안내한다.
5. 원문 비밀번호는 어디에도 저장하거나 기록(log)하지 않는다.
                한계: 이것은 잠금이지 인증이 아니다. 비밀번호 하나로는 누가 들어왔는지 구분할 수 없다. 한 번 공유되면 통제가 끝나고, 사람별 접근 기록도 남지 않는다. 짧은 비밀번호의 단순 해시는 무차별 대입에 약하므로 문장형으로 길게 정한다. 실제 회원 비밀번호 저장에는 솔트와 느린 해시 함수(bcrypt, Argon2 등)를 쓴다. 혼자 또는 신뢰하는 소수가 쓰는 사이트까지가 적정 범위다.

                • 남는 위험은 메일 계정 자체의 보안이다. 이용자가 메일 계정에 2단계 인증을 켜 두면 그 보호를 그대로 이어받는다
                • 과제의 웹앱: 혼자 쓰면 비밀번호 잠금, 동료·고객이 쓰면 이메일 인증코드로 시작한다

                  내 업무에서 AI 자동화 대상 고르기

                  직무 전체가 아니라 과업 단위로 업무를 나누고, 가치와 위험을 기준으로 첫 번째 대상을 고른다. 그다음 스킬로 만들지, 웹앱으로 만들지 정한다.

                    자동화 대상 고르기

                    출발점: 직무가 아니라 과업(task) 단위로 나눈다

                    • “계약 검토를 AI로 자동화한다”는 너무 크다. 계약 검토는 여러 과업의 묶음이고, 과업마다 AI가 잘하는 정도와 틀렸을 때의 비용이 다르다
                    • 과업은 입력 → 처리 → 출력이 분명한 한 덩어리의 일이다. 출력이 누구에게 가는지(나, 동료, 고객, 기관)까지 적는다
                    과업 (예: 사내 법무팀의 계약 검토)입력출력과 받는 사람AI 적합도
                    검토 요청 접수·분류 (계약 유형, 긴급도)요청 메일, 첨부 계약서분류표 → 나높음
                    표준 계약서와 차이점 비교상대방 초안, 사내 표준안변경 조항 목록 → 나높음
                    사내 체크리스트 대조 (손해배상 한도, 준거법 등)계약서, 체크리스트위험 조항 표시 → 나높음 (기준이 문서화된 경우)
                    수정 문구 초안 작성위험 조항, 과거 협상 사례수정안 → 상대방중간 (사람 검토 필수)
                    현업 부서 질문 응대 (“이 조항 괜찮나요?”)질문, 사내 규정답변 → 동료중간 (RAG 후보)
                    최종 승인 판단·서명전체 검토 결과결재 → 회사사람 (책임 주체)

                    여러분의 업무도 같은 표로 10개 안팎의 과업으로 나눌 수 있다. 일주일 업무 일지나 캘린더를 보며 적으면 빠르다.

                    자동화 대상 고르기

                    후보 과업을 평가하는 6가지 기준

                    1빈도와 소요 시간

                    주 1회 이상, 회당 30분 이상이면 절감 효과가 분명하다. 1년에 한 번 하는 일은 자동화보다 그때 Chat에 묻는 편이 낫다

                    2입력이 디지털 텍스트인가

                    메일, 문서, 표, PDF면 바로 시작할 수 있다. 종이·구두·사내 시스템 화면에만 있는 정보는 수집 단계부터 일이 된다

                    3기준이 문서화되어 있는가

                    체크리스트, 규정, 과거 사례가 있으면 AI에게 줄 수 있다. 판단 기준이 머릿속에만 있다면 그것을 적는 일이 첫 작업이다(3강의 스킬)

                    4결과를 검증하기 쉬운가

                    결과가 맞는지 확인하는 데 드는 시간이 직접 하는 시간보다 훨씬 짧아야 한다. 검증이 어려운 일은 AI가 틀려도 알아채기 어렵다

                    5틀렸을 때의 비용

                        신뢰성을 확인하는 방법: 평가 세트를 만들고 기록을 읽는다

                        1성공 기준을 숫자로

                        “잘 분류한다”가 아니라 “테스트 50건 중 48건 이상 정답, 근거 없는 인용 0건”. 무엇이 실패인지 미리 정한다

                        2평가 세트 20~50건

                        실제 업무에서 뽑고, 실제로 틀렸던 사례를 포함한다. 두 명의 전문가가 같은 합격·불합격 판정을 내릴 수 있을 만큼 명확하게, 건마다 참조 정답을 둔다

                        3예외 입력 포함

                        빈 입력, 아주 긴 입력, 범위 밖 질문(§3의 “이혼 재산분할”), 모호한 질문. 이것이 오늘 RAG 완료 보고의 검증 시나리오 4종이다

                        4채점은 규칙 → 모델 → 사람 순

                        인용 번호 존재 여부처럼 코드로 확인할 수 있는 것은 코드로. LLM 채점은 생성 모델과 다른 모델로 하고 사람 판정과 맞춰 본다

                        5한 번이 아니라 여러 번

                        같은 입력에 매번 맞아야 하는 일이면 k번 모두 성공(pass^k)을 본다. 1회 성공률 75%면 3번 연속 성공은 약 42%다

                        6기록을 직접 읽는다

                        점수만 보지 말고 실패한 대화를 읽는다. 원인이 검색인지, 생성인지, 채점인지 기록에서 확인한다. §7의 로그가 이 자료다
